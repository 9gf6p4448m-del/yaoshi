# 長時 SFX「下一件拍品」間歇卡點診斷（2026-09-24）

**結論**：歷史上 `tests/sfx-wiring.test.mjs` 回報的「driveUntil 卡住：下一件拍品／開戰」是**舊測試驅動的輪詢次數預算（`for i<4000`）用完**，不是產品卡死。`998f2fc` 把次數預算換成 5 分鐘牆鐘預算，才是實際的修正；它並非靠跳過鈕掩蓋產品 hang。產品 `index.html`（HEAD `e5df109`）本輪未改。

**白話**：舊版測試只准機器人「看 4000 眼」。一局遊戲要看 2400–4100 眼（看電腦快慢、局長短而定），看完 4000 眼還沒打完就喊「卡住了」，喊的時候遊戲剛好停在哪個畫面就報哪個——而遊戲 7～8 成時間停在「下一件拍品」「開戰」的等待畫面上。

## 條件

- 腳本：[`repro.mjs`](repro.mjs)（原寫於 `scratchpad/sfx-stall/`，移入時只改 `ROOT` 相對路徑與用法註解）。
- 條件同原測：headless Chromium 844×390、`CFG.T=1`、`PW_FX` 全部 `*_MS=1`、solo、`['qingmian']`。
- `--driver=old`：逐字複製 `998f2fc^` 舊驅動（輪詢次數計閒置、閒置 >300 次在任何層按跳過、`--cap` 次上限後判卡）。`--continue=1`：判卡後不拋錯，用同一套點擊邏輯無上限續推最多 6 分鐘，看局會不會自己打完。
- `--driver=new`：`998f2fc` 新驅動（牆鐘 3 秒閒置、只在可見 #duel 按跳過、5 分鐘上限）。
- 注入 `[DEBUG-sfx7]` 包裝 waitMain／startReveal／startBattle／playDuel 等全域函式，只在診斷頁面生效，不改產品檔。

- 狀態分佈：各局輪詢約 70–80% 落在「下一件拍品 ▸（停用）」與「開戰（停用）」，所以預算耗盡時的主鈕文字大多是這兩個，對上歷史症狀。
- 雙向：同一產品下，上限低於該局所需 → 判卡；無上限續推 → 打完（3 局都成立；2 局全程 0 跳過，1 局在判卡後按過 1 次跳過）；上限高於所需 → 通過（4 局）。
- 同 seed 夜數不固定（seed 3 出現 9 夜與 12 夜），局長與機器負載（每次 evaluate 平均 30→75 ms）共同決定所需輪詢數；因此舊預算在慢機或長局才會觸發，表現為「間歇」。

## 限制（據實）

- 事先訂的驗收是「判卡方向」連跑 ≥5 次；實際判卡後續推打完 **3 次**。第 4、5 局兩度因系統記憶體不足被 Claude Code 強制中止（不是腳本錯誤），依規定未自行重跑。
- 歷史卡點發生在較舊的產品版本；本輪證明的是「此機制在健康產品上可完整重現同一症狀」，沒有回到舊版重跑，不能保證每一次歷史事件都是它。
- 新驅動在 seeds 1–3 **幾乎每夜都按了跳過**（新驅動閒置滿 3 秒即按，同一夜最多嘗試 2 次；另在舊驅動紀錄中，「開戰」等待單段連續閒置最長 50.8 秒，見 runs-s3-cap2500-x4 #2 的 `maxIdle`），但舊驅動 0 跳過也能打完，故對決是慢而非卡死。影響：封標／揭盅／受咒都在對決前已響，測試斷言不受影響；但這支測試實際沒有覆蓋任何一場對決的音效。
- 新驅動 5 分鐘預算餘裕約 2.1–2.7 倍（112–141 秒）；記憶體吃緊時單局可達 200–390 秒（舊驅動＋續推的量測），**餘裕會被吃掉**，屆時會出現新形態的「driveUntil 超時」——這也是驅動預算，不是產品卡點。
