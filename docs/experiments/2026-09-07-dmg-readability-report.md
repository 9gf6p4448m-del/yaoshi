### R2 被打的尊閃紅（四版：剪影遮罩，方案 A 判定）
**量測位置改了兩次，這是第三版**：
1. 一版＝該尊**投影方框內全部像素**的平均 → 方框裡七成是背景，訊號被稀釋（p50 5.69）。
2. 二版＝「命中前 vs 閃紅」差分出的遮罩 → 覆審指出**遮罩由刺激選出＝換尺規**（那把尺會自己往有訊號的地方靠）。
3. **三版＝剪影遮罩**：同一時刻拍兩張——把那一尊丟到相機看不到的層再重畫一幀，
   與命中前那一幀差分出「這一尊佔畫面哪些像素」。遮罩由**那一尊在不在**決定，與閃紅完全無關。
   取樣時機也改了：不再等牆鐘 40ms（機器一忙那一格就落到 80–120ms、閃紅早就衰退），
   改成**虛擬時鐘 warp 40ms 再畫一幀**，四張圖（命中前／剪影／+40ms／+200ms）都在同一次凍結裡拍完。
   有效樣本＝拿得到剪影、`maskFrac ≥ 0.1`、而且 **+40ms 那一幀的方框相對命中前位移 ≤ 4px**
   （動了就代表鏡頭或人形在動、剪影對不上），另外窗內不得有燒毀、四格不得落在 `ys:duel-end` 之後；
   被閘門剔掉的逐項計數都印在 `maskDropped`（v10：seed 1 moved 4／tinyMask 1、seed 3 moved 9／tinyMask 2）。
   **Δ200 那一條沒有位移閘門**（686515c 曾加過，第三輪覆審 HIGH-A 判為未經同意的移動及格線，使用者 09-10 裁乙拿掉；修訂 2-B）。

   ⚠️ **warp 這個量法的涵蓋缺口**：它把「遊戲時間往前推 40ms 再畫一幀」當成「命中後 40ms 的畫面」。
   這對**閃紅包絡與鏡頭補間**是對的（兩者都吃同一個時間戳），但它**不涵蓋真實牆鐘下的可見性**——
   真機上這 40ms 會不會被掉幀吃掉、玩家眼睛實際看到幾毫秒的紅，這支治具答不了。
   那一半只有真機試玩答得出來。

### R6 效能與 programs（⚠️ 未驗證）
覆審指出這條的訊號不可信：`duel-perf perf` 每次派的是**當場那一局真實的對決**（可見尊數 14–16、

我報告的 3 對量到 **1.054**——同一份程式碼、兩個結論。**這一條標未驗證。**

三版寫了新治具 `tests/tools/dmg-perf-pairs.mjs`：固定合成 8v8 場景（兩版收到逐位元組相同的 `ys:duel`）、
同一個 session 交錯 N 對（預設 9）、報**逐對比值的中位數與 IQR**，而且**同一版連跑兩次的比值也一起報**
——那就是這個訊號的噪音底；三角形／draw call 不相同的那一對直接作廢。
**要在沒有其他 agent 負載的時段跑**（主對話會安排），跑完才填數字。

仍然成立的那一半：`renderer.info.programs.length` 逐場 新版 `[22, 28, 28, 28]`、基準 `[22, 28, 28, 28]` 完全相同
