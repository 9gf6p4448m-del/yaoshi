# X 甲口徑：逐鏈單夜子賽局窮舉——凍結驗收

日期：2026-09-24。狀態：**凍結**（實作前訂定；之後任何會讓通過機率上升的改動，都要先寫明原標準錯在哪，並取得使用者針對該條的明確同意）。
裁定來源：使用者於 2026-09-24 就[新發布裁定提案](../2026-09-23-destiny/release-decision-proposal-x.md)選**甲**，四項設計題全照建議：收益＝淨生命＋經驗估值、每鏈 3 個自然局面、26 選項網格、差分判定＋普通與原案。

## 0. 凍結前修正（對上述建議的兩處加嚴，理由已向使用者回報）

- **局面活性**：天命真版要兩件材料都在袋中才生效（`index.html:3463-3480`）。若只用「持一件、另一件在市場」，開與關的收益表會完全相同，差分判定恆真。因此每個局面都必須通過 §3 的活性檢查。
- **金額級距**：保守標上限是 `floor(life/6)`（`index.html:3276-3279`），生命 50 時只有 8，固定級距 `{1,3,6,10,15}` 對保守標不合法。改成依各席當下合法上限換算，選項數仍是 26（§4）。

## 1. 來源與環境

- 產品來源固定為 commit `d63f03e` 的 `index.html`（與 v2–v11 相同），用 `git show` 讀取，並記錄 blob 與 SHA256。不改 `index.html`、不改 v2–v11 的 adapter。
- 正式跑數要求工作樹乾淨；runner 核對來源 hash，不符就拒跑。
- 支配與 freeLunch 的判定直接呼叫凍結的 `analyzeEvent`（`index.html:7998`），不另寫判定邏輯。

## 3. 代表性局面（每臂 3 個，前／中／後期）

- **來源**：凍結引擎、solo 四席、H9 預設桌設定（`arms.json` 的 `ordinaryH9` normal；天命臂用 `destinyGame` 的 original 設定），種子從 `10001` 起遞增；取每夜拍賣**開標前**（市場已抽、尚無任何提交）的狀態，用 `captureGameStateSnapshot` 保存。
- **時段視窗**：前期＝第 1–4 夜、中期＝第 5–8 夜、後期＝第 9–12 夜。每個視窗取第一個合格局面（種子由小到大、同種子夜數由小到大）。
- **合格條件（全部成立）**：
  1. 四席全部存活。
  2. 有一席持鏈者 H，符合下列之一，並依序優先：(a) 生效型：H 袋中已有該鏈兩件材料（天命臂另需 `activeTrueDestiny(H,鏈)` 為真）；(b) 追件型（僅限普通鏈）：H 持一件，另一件在本夜市場。
  3. 市場至少 2 件非詛咒物，而且 §4 的物件 X、Y 都有估值（§5 樣本數 ≥30）。
  4. 26 個選項對四席在該局面都合法（以 `enumerateLegalAuctionSubmissions` 核對）。
  5. **活性**：開與歸零兩張完整收益表（×1.0 估值）至少有一格、至少一席的收益不同。不成立就跳過，繼續找下一個。
- 視窗內找到種子 `12000` 仍無合格局面時，該局面標 `incomplete`。

## 4. 網格（每席 26 個選項，四席共用標籤）

- 物件 X：本夜市場中估值最高的非詛咒物；追件型局面則固定 X＝H 缺的那件材料。物件 Y：其餘非詛咒物中估值最高者。
- 級距 `L1..L5`＝`{1, ⌈c/4⌉, ⌈c/2⌉, ⌈3c/4⌉, c}`，c＝該席在當下局面、該標型的合法單筆上限（保守標＝`consCapFor`；押命＝扣掉買路錢後的 `budgetFor`）。不同級距換算到同一金額時照樣保留（會形成平手，由差分判定處理）。
- 選項：空標 ×1；只標 X（L1–L5 × 保守／押命）×10；只標 Y（同上）×10；X 與 Y 同標（L1–L5，保守標，兩筆同級距）×5。全部用 `keep`；不含毒標、盯印、押寶夜（押寶夜局面視為不合格）。
- 其餘市場物件四席都不標；四席均以 `humanBids` 提交，不走 `aiBids`。

## 5. 收益

- 每席收益＝（本夜拍賣＋`applyAutomaticNightSettlement` 夜戰＋夜末後的生命）−（開標前生命）＋Σ（本夜得標物件的估值）。每個組合都從同一個 snapshot 還原，包括兩條 RNG 游標。
- **估值表**：另跑一次凍結量測。來源 `d63f03e`、H9 normal 全 AI 桌、種子 `30001..32000`，記錄每次得標的物件 id 與實付標額（不含買路錢）；估值＝平均實付標額。表格連同來源 hash 與樣本數落檔。
- **敏感度**：每個局面都用估值 ×0.5、×1.0、×1.5 各跑一次。

## 6. 判定

- 對每個局面、每個估值倍率，分別用 `analyzeEvent` 算開與歸零兩張表：
  - **新支配**：開的表裡出現支配選項（`strict:false` 也算），而且歸零的表在同一席、同一選項上沒有這個支配。
  - **新 freeLunch**：開的表中，存在一個選項，四席全選它時每席收益都 >0，而歸零的表在同一選項上不是如此。
- 局面判定：三個倍率都沒有新支配也沒有新 freeLunch＝**pass**；三個倍率都有＝**fail**；結論隨倍率改變＝**incomplete（估值敏感）**。
- 臂判定：三個局面都 pass＝pass；任一 fail＝fail；其餘＝incomplete。
- **X（甲口徑）整體**：12 臂全 pass 且 §7 兩項對照都通過，才可把契約的 `sixOfFour` 記為 `pass (single-night subgame scope)`。任一 fail／incomplete 就照實記錄，不得改網格、局面或倍率重跑取綠。

## 7. 檢查器本身的鑑別力（必過）

1. **正對照**：在測試副本中注入一條突變鏈，讓持有者得標時實付 0（不改產品檔，用測試內的 hook 注入）。對至少一個局面，檢查器必須回報新支配或新 freeLunch；不報警＝檢查器無效，修檢查器，不修對照。
2. **原閘門回歸**：GAME_DESIGN 六之四要求的舊版試膽大會必須仍被 `analyzeEvent` 報警，修正版則不報警。

## 9. 修訂 1（2026-09-24，使用者明確同意；取代 §6 的支配定義與 §7.1 的失敗處置，其餘條文不變）

**原標準錯在哪**：§6 的支配沿用 `analyzeEvent` 的全格不劣判定。實作探針（`h9-normal` 種子 10009 第 6 夜、water 生效型、H＝座位 3，四席生命 43／8／24／45）顯示：§7.1 的「持有者得標實付 0」突變已經確認生效（H 押命 45 標 X，歸零表 −45、開的表 +4），但兩張完整表（456,976 格）在三個倍率下都沒有支配、也沒有 freeLunch。多物件、多金額的拍賣裡，總有某些對手組合讓別的選項較好，全格不劣幾乎不可能成立，所以原判準連明顯壞掉的鏈都抓不到，pass 沒有意義。**為什麼現在才知道**：這是第一次把判準跑在真實的拍賣收益表上；原閘門是為二選一這類離散事件設計的。

**新判準（ε-近似支配，ε＝1 命，事先固定、不校準）**：
- 某席 i 的選項 A，最大遺憾＝max over 對手組合 k [ max_B payoff_i(B,k) − payoff_i(A,k) ]。最大遺憾 ≤ 1 就是**近似支配**。
- **新支配**改為：開的表中某席某選項近似支配，但歸零表同一席同一選項不是。`analyzeEvent` 的精確支配照樣計算並列入報告，但不作判定依據。freeLunch 定義不變。
- 最大遺憾用新寫的程式計算，必須先過兩個回歸：試膽大會舊版報警（精確支配的遺憾是 0）；修正版在 ε＝1 下**不**報警。任一不符，就是計算有誤，修計算。

**§7.1 改為**：原突變（持有者得標實付 0，不加強）在上述探針局面，ε＝1 下必須報新支配或新 freeLunch。**若不報警，X 甲口徑終止**，改依提案選項丁處理，並附上這份探針證據。不得調 ε、不得換突變、不得換局面重試。

**歧義補定（實作 agent 提出，照建議定案）**：
1. §5 估值：照 H9 normal 原樣跑（座位 0 為 scriptedBids），四席得標都計入；另附一欄「只算 AI 座位」的估值供比對，但判定用四席版。
2. §3 天命臂用 `original-ai-off` 設定；命函取 `scratchpad/destiny-formal-v1/private-draws.json`（正式跑同一份，記錄 SHA256）。
3. §5 收益包含開標後、夜戰前的 `resolveShrines`，四席一律不燒香。
4. §4 只在 `resolveAuction` 期間暫時拿掉四席 AI 身分，結算後還原。
5. §3 同一型別有多席合格時，取座位號最小者。
6. §1「工作樹乾淨」只檢查已追蹤檔案（未追蹤的 `.agents/` 永不提交）；來源 hash 核對不變。
